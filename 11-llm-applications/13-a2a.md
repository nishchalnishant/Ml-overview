# A2A — Agent2Agent Protocol

---

## The problem A2A solves

MCP solves agent-to-*tool* communication: a model calling a stateless function and getting a structured result back. It does not solve agent-to-*agent* communication — handing an entire unit of work to another autonomous agent that may run on different infrastructure, use a different model, keep its own long-running state, and report progress over time.

Before A2A, teams building multi-agent systems solved this ad hoc:
- custom REST endpoints per agent, incompatible across teams
- no standard way to discover what another agent can do before calling it
- no standard task lifecycle — is the other agent still working? did it fail? can I cancel it?
- no standard way to exchange rich, multi-part results (text, files, structured data) between agents built by different vendors

**The core insight**: agent collaboration is a different layer from tool calling. **MCP is agent-to-tool** — fine-grained, synchronous-feeling, called many times per turn as a model reasons. **A2A is agent-to-agent** — coarse-grained, often long-running, a handoff of an entire goal rather than a single function call. You would A2A-call another company's agent to "research this topic and report back," but you would not want to hand that same agent a `read_file` tool call — that's MCP's job, one layer down.

**What A2A standardizes**:
- how an agent advertises its capabilities to other agents (Agent Cards)
- how a task is submitted, tracked, and updated over its lifecycle
- how multi-part messages (text, files, structured data) are exchanged
- how streaming/incremental progress is reported for long-running work
- how agents discover each other without hardcoded integration

---

## 1. Architecture: Client Agent and Remote Agent

A2A has a two-role model, and unlike MCP's Host/Client/Server split, both sides are peers — full agents, not passive servers.

### Client agent

The agent initiating the handoff. It decides *that* work should be delegated and *to whom*, constructs a `Task`, and sends it to the remote agent. It does not know or care how the remote agent does its job internally — only its declared inputs, outputs, and capabilities.

### Remote agent

The agent receiving the task. It exposes an **Agent Card** describing what it can do, runs its own internal logic (which may itself use MCP tools, sub-agents, or another model entirely), and returns results through the task lifecycle. It is a black box to the client — the same task could be fulfilled by a Python service, a different LLM, or a human-in-the-loop system, and the client wouldn't know the difference.

```
Client Agent (Research Orchestrator)
   │  "A2A: discover Agent Card"
   ▼
Remote Agent (Analysis Agent)
   │  exposes: AgentCard { name, skills, input/output modes }
   │  runs: its own internal pipeline (maybe MCP tools inside)
   ▼
Task { id, status, artifacts } ──> returned to Client Agent
```

**What breaks if you conflate this with MCP's model**: treating a remote agent like an MCP server (call it once, get a synchronous result, done) throws away the parts of A2A that matter — task state, streaming updates, multi-turn clarification, and multi-part artifacts. A2A tasks are not function calls; they're delegated goals that may take seconds or hours and may need back-and-forth.

## 2. Agent Cards: capability discovery

**The problem**: before delegating work, a client agent needs to know what a remote agent can actually do, what inputs it expects, and how to reach it — without a human hardcoding that integration.

**The core insight**: an Agent Card is a self-describing manifest, conceptually similar to an OpenAPI spec or an MCP `tools/list` response, but describing an *agent's* skills rather than a server's functions. It's typically published at a well-known URL (`/.well-known/agent.json`) so any client can discover it by URL alone.

```json
{
  "name": "Analysis Agent",
  "description": "Performs statistical analysis on structured research findings and returns a summary with confidence scores.",
  "url": "https://agents.internal/analysis-agent",
  "version": "1.0.0",
  "capabilities": {
    "streaming": true,
    "pushNotifications": false
  },
  "skills": [
    {
      "id": "analyze-findings",
      "name": "Analyze Findings",
      "description": "Runs descriptive and inferential statistics over a set of research findings and returns key metrics plus a plain-language summary.",
      "inputModes": ["text", "application/json"],
      "outputModes": ["text", "application/json"]
    }
  ]
}
```

**Why the description matters as much as in MCP**: just like MCP tool descriptions are written for a model to decide *when* to call them, Agent Card skill descriptions are consumed by another agent (or the model orchestrating it) deciding whether this remote agent is the right one to delegate to. A vague skill description produces bad delegation decisions the same way a vague tool description produces bad tool calls.

## 3. The Task Lifecycle

**The problem**: a single request/response model doesn't fit work that takes time, may need clarification mid-flight, or produces results incrementally.

**The core insight**: A2A models delegated work as a `Task` with an explicit state machine, not a fire-and-forget call. The client can check status, receive streamed updates, or get notified on completion instead of blocking synchronously.

```
submitted -> working -> input-required -> working -> completed
                                        \-> failed
                                        \-> canceled
```

- **submitted** — task created, not yet picked up
- **working** — the remote agent is actively processing
- **input-required** — the remote agent needs clarification from the client before it can continue (distinct from failure — the task is paused, not dead)
- **completed** — done, artifacts available
- **failed** / **canceled** — terminal, no artifacts (or partial artifacts on cancellation)

### Messages and Parts

Each turn in a task exchanges a `Message` made of one or more `Part`s — the multi-part structure lets a single message carry mixed content (a text explanation plus a file plus structured JSON) instead of forcing everything into a string.

```json
{
  "role": "agent",
  "parts": [
    {"type": "text", "text": "Analysis complete. Key finding: 23% variance reduction."},
    {"type": "data", "data": {"mean": 4.2, "p_value": 0.03}},
    {"type": "file", "file": {"name": "report.pdf", "mimeType": "application/pdf", "bytes": "..."}}
  ]
}
```

### Client call: `send_task`

```python
# Conceptual client-side call — discover the card, then submit work
agent_card = await discover_agent_card("https://agents.internal/analysis-agent")

task = await send_task(
    agent_url=agent_card["url"],
    message={
        "role": "user",
        "parts": [{"type": "data", "data": {"findings": research_findings}}]
    }
)

while task["status"]["state"] not in ("completed", "failed", "canceled"):
    task = await get_task(task["id"])   # poll, or subscribe to streamed updates

result_parts = task["artifacts"][0]["parts"]
```

## 4. Transport and Streaming

A2A is built on HTTP with JSON-RPC-style requests, and supports Server-Sent Events for streaming task updates — deliberately similar to MCP's transport choices, since both protocols solve "how do two processes exchange structured messages" and reuse the same well-understood primitives rather than inventing new ones.

**Streaming matters more for A2A than MCP** because tasks are coarse-grained and long-running: a research agent might take 30 seconds and want to stream partial findings, rather than leaving the client blocked with no visibility.

```python
# Conceptual streaming subscription
async for update in subscribe_to_task(task_id):
    if update["type"] == "status-update":
        print(f"Status: {update['status']['state']}")
    elif update["type"] == "artifact-update":
        print(f"Partial result: {update['artifact']}")
```

**Push notifications**: for tasks that may run far longer than a client wants to hold a connection open, an agent can register a webhook URL and be notified on completion instead of polling or streaming.

## 5. A2A vs MCP — where each one fits

These are complementary, not competing — most real multi-agent systems use both, at different layers.

| | MCP | A2A |
|---|---|---|
| Relationship | Agent ↔ Tool | Agent ↔ Agent |
| Granularity | Fine-grained (one function call) | Coarse-grained (one delegated goal) |
| Call frequency | Many times per model turn | Once per handoff, possibly long-running |
| State | Servers are stateless per call | Tasks carry explicit lifecycle state |
| Discovery | `tools/list` on a server | Agent Card at a well-known URL |
| Typical duration | Milliseconds–seconds | Seconds–hours |
| Result shape | Single structured tool result | Task with artifacts, possibly streamed incrementally |

**The practical pattern**: an orchestrator agent A2A-delegates a subgoal ("research topic X") to a specialist agent. That specialist agent, internally, uses MCP servers (web search, a notes database) to actually do the work. From the orchestrator's point of view it never sees the specialist's MCP tool calls — those are an implementation detail one layer down, exactly as intended by keeping the two protocols separate.

```
Orchestrator Agent
   │  A2A: delegate "research topic X"
   ▼
Research Agent  ──MCP──> web-search server
                ──MCP──> notes server
   │  A2A: task completed, artifacts = [summary, sources]
   ▼
Orchestrator Agent (continues with the result)
```

**What breaks if you use the wrong one**: using A2A for every tool call adds task-lifecycle overhead (IDs, state tracking, artifact wrapping) to something that should be a single synchronous function call. Using MCP to call another full agent throws away task state, streaming, and the ability for that agent to ask for clarification mid-task — you'd be forcing an agent-shaped problem through a tool-shaped interface.

## 6. Building an A2A Server (Remote Agent side)

```python
from fastapi import FastAPI
import uuid

app = FastAPI()

AGENT_CARD = {
    "name": "Analysis Agent",
    "description": "Runs statistical analysis on structured findings.",
    "url": "https://agents.internal/analysis-agent",
    "version": "1.0.0",
    "capabilities": {"streaming": True},
    "skills": [{
        "id": "analyze-findings",
        "name": "Analyze Findings",
        "description": "Computes descriptive stats and a plain-language summary from findings.",
        "inputModes": ["application/json"],
        "outputModes": ["application/json", "text"]
    }]
}

tasks = {}

@app.get("/.well-known/agent.json")
async def get_agent_card():
    return AGENT_CARD

@app.post("/tasks")
async def create_task(request: dict):
    task_id = str(uuid.uuid4())
    tasks[task_id] = {"id": task_id, "status": {"state": "submitted"}, "artifacts": []}

    tasks[task_id]["status"]["state"] = "working"
    findings = extract_data_part(request["message"]["parts"])
    analysis = run_statistical_analysis(findings)   # the agent's actual internal logic

    tasks[task_id]["status"]["state"] = "completed"
    tasks[task_id]["artifacts"] = [{
        "parts": [
            {"type": "text", "text": analysis["summary"]},
            {"type": "data", "data": analysis["metrics"]}
        ]
    }]
    return tasks[task_id]

@app.get("/tasks/{task_id}")
async def get_task_status(task_id: str):
    return tasks[task_id]
```

## 7. Building an A2A Client (Client Agent side)

```python
import httpx

async def send_task(agent_url: str, message: dict) -> dict:
    async with httpx.AsyncClient() as client:
        card = (await client.get(f"{agent_url}/.well-known/agent.json")).json()
        response = await client.post(f"{card['url']}/tasks", json={"message": message})
        return response.json()

async def delegate_analysis(findings: dict) -> dict:
    task = await send_task(
        agent_url="https://agents.internal/analysis-agent",
        message={"role": "user", "parts": [{"type": "data", "data": findings}]}
    )
    if task["status"]["state"] == "completed":
        return task["artifacts"][0]["parts"]
    raise RuntimeError(f"Task did not complete: {task['status']}")
```

In a real pipeline: an orchestrator's model decides *that* delegation is needed (similar to a tool-use decision), the host-equivalent code constructs the `Task` and calls `send_task`, and the artifacts come back to be injected into the orchestrator's own context — structurally parallel to MCP's tool-result injection, just at a coarser grain.

## 8. Security

### The problem

A2A hands real work — and often real data — to an agent you may not control, potentially across a trust boundary (another team, another company). The remote agent's internal behavior is opaque; you only see its declared skills and the artifacts it returns.

**The core insight**: since the remote agent is a black box, security has to be enforced primarily at the boundary — what you send it, what you accept back, and what identity/authorization governs the exchange. You cannot sandbox someone else's agent internals the way an MCP host can sandbox its own tool servers.

### Authentication and authorization

Agent Cards can declare required auth schemes (API key, OAuth2, mTLS). Treat cross-organization A2A calls the same as any external API integration — never send credentials or PII in a task payload without confirming the remote agent's declared trust level and data-handling policy.

```python
AGENT_CARD["authentication"] = {
    "schemes": ["oauth2"],
    "credentials": "https://agents.internal/analysis-agent/oauth-info"
}
```

### Validating returned artifacts

**The problem**: a remote agent's output — especially free-text parts — can contain adversarial content, just like an MCP tool result can. If the client agent's model reads the artifact text directly into its context, prompt injection from a malicious or compromised remote agent is possible.

**Defenses** — the same posture as MCP tool-result injection, applied one layer up:
- treat artifact `text` parts as untrusted data, not instructions, when injecting into the client's model context
- validate `data` parts against an expected schema before using them programmatically
- keep any high-risk follow-up action (based on a remote agent's output) behind explicit confirmation, especially for agents outside your own trust boundary

### Task-level scoping

**The problem**: a client agent might over-share context when delegating — passing an entire conversation history to a remote agent that only needed one field.

**The core insight**: construct the smallest task payload that satisfies the remote agent's declared input schema. This limits blast radius if the remote agent is compromised or logs its inputs.

### Timeouts and cancellation

Long-running tasks need a cancellation path — a remote agent that never returns cannot be allowed to block the client indefinitely.

```python
import asyncio

async def delegate_with_timeout(agent_url, message, timeout_s=30):
    task = await send_task(agent_url, message)
    try:
        return await asyncio.wait_for(poll_until_done(task["id"]), timeout=timeout_s)
    except asyncio.TimeoutError:
        await cancel_task(agent_url, task["id"])
        raise
```

## 9. Multi-Agent A2A + MCP in Practice

This is the pattern the hands-on project in [`17-projects/04-multi-agent-a2a-mcp/`](../17-projects/04-multi-agent-a2a-mcp/README.md) implements end-to-end: three agents, each with their own MCP servers for internal tool access, coordinating via A2A for the handoffs between them.

```
Driver
  │  A2A: POST /tasks (goal)
  ▼
Research Agent  ──MCP──> notes-server
  │  A2A: POST /tasks (findings)
  ▼
Analysis Agent  ──MCP──> stats-server
  │  A2A: POST /tasks (findings + analysis)
  ▼
Report Agent    ──MCP──> filesystem-server, notes-server
```

Each agent box is its own process, running an A2A server (to receive delegated tasks) and one or more MCP clients (to use its own tools internally). This is the clean layering the two protocols are designed to produce: **A2A moves work between agent boundaries; MCP moves capability within an agent.** Neither protocol tries to do the other's job — an agent never uses A2A to call its own filesystem tool, and it never uses MCP to hand off an entire subgoal to a peer agent.

**What breaks without this separation**: collapsing both into one protocol either forces every internal tool call to carry task-lifecycle overhead it doesn't need (using A2A for everything), or forces cross-agent handoffs through a stateless synchronous interface that can't represent "still working" or "need clarification" (using MCP for everything).

## Interview Angles

**Q: What is the A2A (Agent2Agent) protocol, and how is it different from MCP?**
A: MCP standardizes **agent-to-tool** communication — a model calling a stateless function (search a database, read a file) and getting a structured result. A2A standardizes **agent-to-agent** communication — one autonomous agent delegating an entire unit of work to another, potentially across organizational or infrastructure boundaries. The distinction is granularity and statefulness: MCP calls are fine-grained and typically synchronous; A2A tasks are coarse-grained, can be long-running, carry explicit lifecycle state (submitted/working/input-required/completed), and can stream incremental progress. In practice they compose: an orchestrator A2A-delegates a subgoal to a specialist agent, and that specialist internally uses MCP tools to actually do the work — the orchestrator never sees the specialist's tool calls.

### Q: Why does A2A need an explicit task lifecycle (submitted/working/input-required/completed/failed) instead of just a synchronous request/response like a typical API call? [Hard]
A: Because the work being delegated is not a single deterministic function call — it's handed to another autonomous agent whose internal reasoning may take arbitrary time, may need to pause for clarification, or may fail partway through. A synchronous call can't represent "I'm still working" versus "I need more information from you" versus "I failed" — collapsing all of those into a single blocking response either times out prematurely on long tasks or silently loses the distinction between a paused task and a dead one. The `input-required` state specifically matters: without it, an agent that needs clarification has no way to signal "don't give up on me, ask me something" instead of just failing outright, which would force the client into blind retries instead of a real back-and-forth.

**Cross-questions to expect:**

- *Could you build A2A functionality using just MCP?* -> Not cleanly. You could hack a "delegate to another agent" MCP tool, but MCP tools are modeled as stateless single-call functions returning one result — you'd lose the task lifecycle, streaming updates, and Agent Card capability discovery that A2A provides natively. You'd be reimplementing a chunk of A2A inside an MCP tool, which is exactly the kind of "every team reimplements the same thing differently" problem both protocols exist to prevent.
- *How does Agent Card discovery compare to MCP's `tools/list`?* -> Structurally similar — both are a manifest a client fetches before calling anything, describing available capabilities with enough detail (name, description, input/output schema) for an automated decision-maker (a model or an orchestrating agent) to select the right one. The difference is what's being described: MCP describes individual functions; Agent Cards describe an agent's skills as a whole, plus protocol-level capabilities like whether it supports streaming or push notifications.
- *Why keep A2A and MCP as separate protocols instead of one unified protocol?* -> Because they optimize for different things. MCP optimizes for low-overhead, high-frequency, synchronous-feeling tool calls — adding task IDs and lifecycle state to every function call would be pure overhead. A2A optimizes for coarse-grained, potentially long-running, stateful handoffs between autonomous peers — collapsing that into a stateless function-call model would lose the ability to represent "still working" or "need clarification." Keeping them separate lets each protocol's design match its actual usage pattern, the same reasoning that keeps MCP's Tools and Resources separate despite both being "data the model can get."

**Trap:** Assuming A2A replaces MCP in an agentic system, or that you'd pick one over the other. They operate at different layers — A2A for the edges between agent boundaries, MCP for the tools inside each agent. A well-architected multi-agent system typically uses both simultaneously, not one instead of the other. If an interviewer asks "would you use A2A or MCP here," the strong answer identifies whether the boundary in question is agent-to-agent or agent-to-tool, rather than picking a favorite.
